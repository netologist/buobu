# TD-002: Non-Standard UUIDv7 Implementation and ID Generation Fragmentation

## Status

**Open / Accepted Debt** — 2026-09-12

## Context

Entity identifiers across `buobu` are generated using two competing mechanisms:
1. Custom implementation of `uuidv7()` in [`src/lib/uuid.ts`](file:///Users/hozgan/devbox/personal/buobu-oss/src/lib/uuid.ts).
2. Direct `nanoid()` invocations in several stores and factories.

Additionally, the `uuidv7` package (`^1.2.1`) is declared as a dependency in [`package.json`](file:///Users/hozgan/devbox/personal/buobu-oss/package.json) but is never imported anywhere in the codebase.

### The RFC 9562 Incompatibility

The custom `uuidv7()` function in `src/lib/uuid.ts` produces a **37-character** string instead of the standard **36-character** RFC 9562 format (`8-4-4-4-12`):

```ts
const parts = [
  hexTimestamp.substring(0, 8),
  hexTimestamp.substring(8, 12) + hexMillis, // 4 + 1 = 5 chars (expected: 4)
  '7' + hexCounter.substring(0, 2),          // 1 + 2 = 3 chars (expected: 4)
  (parseInt(hexCounter.substring(2, 3) || '0', 16) & 0x3 | 0x8).toString(16) +
    hexRandom.substring(0, 2),               // 1 + 2 = 3 chars (expected: 4)
  hexRandom.substring(2)                     // 14 chars (expected: 12)
];
```

Resulting format: `xxxxxxxx-xxxxx-xxx-xxx-xxxxxxxxxxxxxx` (37 characters).

Because of this malformed segment layout:
- `isValidId(uuidv7())` returns `false` (as confirmed by the explicit assertion in [`src/lib/__tests__/uuid.test.ts`](file:///Users/hozgan/devbox/personal/buobu-oss/src/lib/__tests__/uuid.test.ts#L69)).
- Standard external UUID parsers (PostgreSQL `uuid` column, standard validators, external APIs) reject IDs generated by this function.

### Why It Was Not Replaced Immediately

`buobu` is a Local-First application. Thousands of IndexedDB primary keys on existing client browsers and test mocks already store 37-character IDs generated by this function. Changing the generator immediately without a migration strategy risks primary key mismatches, replication collisions, or breaking existing stored database state.

## Current Mitigation

- The custom generator in `src/lib/uuid.ts` remains intact to preserve backwards compatibility for existing local IndexedDB records.
- Tests in `src/lib/__tests__/uuid.test.ts` document and verify the existing 37-character behavior.

## Remediation Paths

### Path A: Standardize on RFC 9562 `uuidv7` (Recommended)
1. Replace the custom function with the official `uuidv7` package already present in `package.json`.
2. Implement an ID migration/normalization utility during RxDB schema initialization that accepts both 36-char and 37-char IDs.
3. Update `isValidId` regex to accept standard 36-char UUIDs while gracefully handling legacy 37-char strings during the transition window.

### Path B: Consolidate to NanoID
1. Deprecate `uuidv7` and adopt `nanoid` uniformly across all domain entities (tasks, habits, notes, swimlanes, boards).
2. Remove the unused `uuidv7` npm package from `package.json`.
